1. JWT 鉴权流程

鉴权流程步骤说明

步骤动作组件说明
①登录请求客户端 → 网关 → 认证服务POST /api/auth/login，携带 username + password
②密码校验认证服务 → MySQLbcrypt 校验密码哈希，查 user 表
③签发 Token认证服务 → Redis → 网关 → 客户端生成 Access Token（30min）+ Refresh Token（7day），Refresh 存入 Redis 白名单
④API 请求客户端 → 网关Header: Authorization: Bearer <access_token>
⑤JWT 验证网关 → Redis无状态验证签名 + 过期时间 + Redis 黑名单检查（登出过的 Token）
⑥路由分发网关 → 微服务解析 JWT claims，将 userId / roles 注入请求头转发
⑦~⑨Token 刷新客户端 → 认证服务 → RedisAccess 过期后用 Refresh 换新对，Refresh 验证 Redis 白名单 + 旋转（旧 Refresh 失效）
⑩~⑫登出客户端 → 网关 → Redis将当前 Token 加入 Redis 黑名单（TTL = Token 剩余有效期），客户端清除本地存储

2. Token 结构与刷新机制

JWT Payload (Claims) 结构

// Access Token Payload — 短期令牌（30分钟） { "iss": "oa-auth-service", // 签发方 "sub": "1024", // userId "aud": "oa-gateway", // 接收方 "iat": 1724923200, // 签发时间 : 1724925000, // 过期时间 (iat + 30min) "jti": "a1b2c3d4-e5f6-7890", // 唯一标识 (防重放) "name": "周锐杰", // 用户姓名快照 "roles": ["MANAGER", "APPROVER"], // 角色编码列表 "org_id": 5, // 组织ID "perms": ["task:approve", "doc:read"] // 权限码 (可选, 减少DB查询) } // Refresh Token Payload — 长期令牌（7天） { "iss": "oa-auth-service", "sub": "1024", "iat": 1724923200, : 1725528000, // iat + 7天 "jti": "r9s8t7u6-v5w4-x3y2", // 不同于 Access 的 jti "type": "refresh" // 标记为刷新令牌 }

Token 刷新策略 — 滑动过期 + 旋转

Refresh Token 旋转（Rotation）：每次用 Refresh Token 换取新 Access Token 时，旧 Refresh Token 立即失效（从 Redis 白名单删除），同时签发新的 Refresh Token。这样即使 Refresh Token 被窃取，攻击者最多只能使用一次，合法用户下次刷新时会发现 Token 失效从而触发重新登录。

密码安全策略

策略规则实现
哈希算法bcrypt, cost=12BCryptPasswordEncoder（Spring Security）
密码复杂度≥8位，含大小写+数字+特殊字符正则校验 ^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[@$!%*?&]).{8,}$
登录失败锁定连续5次失败 → 账号锁定30分钟Redis 计数 login_fail:{userId}，TTL=30min

3. RBAC 权限模型

双层权限控制：
1. 功能权限（Action Level）：角色 → 权限码 → API 接口，决定能否调用某接口
2. 数据权限（Data Level）：数据范围 → SQL 拦截，决定能看到哪些数据行
例如「部门经理」角色有 task:approve 权限（功能），数据范围为 DEPT_AND_SUB（只能审批本部门及下属部门的任务）

5. 接口级访问控制

注解式权限控制（Spring Security + 自定义注解）

// 自定义权限注解 @Target({ElementType.METHOD, ElementType.TYPE}) @Retention(RetentionPolicy.RUNTIME) @PreAuthorize("hasPermission(#request, 'task:approve')") public @interface RequirePermission { String value(); } // Controller 层使用 @RestController @RequestMapping("/api/tasks") public class TaskController { // 审批通过 — 需要 task:approve 权限 @PostMapping("/{id}/complete") @PreAuthorize("hasAuthority('task:approve')") public ApiResponse completeTask(@PathVariable Long id, @RequestBody @Valid TaskCompleteDTO dto) { // 额外校验: 当前用户是否是该任务的 assignee taskService.validateAssignee(id, SecurityUtils.getCurrentUserId()); return ApiResponse.success(taskService.complete(id, dto)); } // 驳回 — 需要 task:reject 权限 @PostMapping("/{id}/reject") @PreAuthorize("hasAuthority('task:reject')") public ApiResponse rejectTask(@PathVariable Long id, @RequestBody @Valid TaskRejectDTO dto) { taskService.validateAssignee(id, SecurityUtils.getCurrentUserId()); return ApiResponse.success(taskService.reject(id, dto)); } // 转办 — 需要 task:transfer 权限 @PostMapping("/{id}/transfer") @PreAuthorize("hasAuthority('task:transfer')") public ApiResponse transferTask(@PathVariable Long id, @RequestBody @Valid TaskTransferDTO dto) { taskService.validateAssignee(id, SecurityUtils.getCurrentUserId()); return ApiResponse.success(taskService.transfer(id, dto)); } // 待办列表 — 数据权限拦截 @GetMapping @PreAuthorize("hasAuthority('task:read')") public ApiResponse<PageResult<TaskVO>> getTasks(TaskQueryDTO query) { // DataScopeInterceptor 自动注入数据范围条件 // EMPLOYEE → WHERE assignee_id = currentUser // MANAGER → WHERE assignee_id IN (deptUsers) OR assignee_id = currentUser return ApiResponse.success(taskService.findMyTasks(query)); } }

数据权限 SQL 拦截器原理

拦截器根据 JWT 中的 roles 和 org_id 自动注入数据范围：
• ALL — 不注入额外条件
• DEPT_AND_SUB — AND org_id IN (SELECT id FROM organization WHERE path LIKE CONCAT((SELECT path FROM organization WHERE id=?), '%'))
• SELF — AND assignee_id = ?（当前用户ID）
开发者无需手写数据范围判断，统一由拦截器处理，避免遗漏。

安全设计总原则：
纵深防御 — 不依赖单一安全层，认证 + 授权 + 数据权限 + 网络策略 + 审计日志层层把关
最小权限 — 每个角色和微服务只授予完成职责所需的最小权限
默认拒绝 — 未显式允许的访问一律拒绝（NetworkPolicy + SecurityContext + API 鉴权）
不可篡改 — 审批记录和操作日志只追加不修改，确保可追溯
